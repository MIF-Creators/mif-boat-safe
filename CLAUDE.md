# CLAUDE.md

Инструкции для Claude Code в репозитории `mif-boat-safe`. Читай этот файл
целиком перед любой работой.

## Проект

Учебная система управления флотом автономных лодок в бассейне. Три программы
общаются через MQTT-брокер (Mosquitto):

- `system/navigation_server/` — камера над бассейном, распознаёт ArUco-маркеры
  и публикует позиции лодок (`nav/{id}/position`);
- `system/vehicle/` — код лодки на Raspberry Pi: получает миссию и позицию,
  управляет моторами через GPIO (на ПК без `RPi.GPIO` работает заглушка);
- `system/control_center/` — Flask-сервер и веб-интерфейс оператора;
- `system/common/` — общий контракт: топики (`topics.py`), сообщения
  (`messages.py`), настройки (`config.py`). Изменения здесь затрагивают все
  три программы.

`legacy/` — старый код, не трогать.

План рефакторинга и спецификации задач: `docs/refactoring-plan.md`.

## Окружение

- Python 3.13 (как в CI). Основная машина разработчика — Windows, PowerShell.
- Виртуальное окружение: `venv` в корне репозитория.
- Тесты: `python -m pytest` (из корня репозитория).
- Линтер так же, как в CI: `python -m ruff check system tests --select E9,F63,F7,F82`
  (набор правил расширяется задачами этапа 2 — бери актуальную команду из
  `.github/workflows/ci.yml`).

## Процесс работы над задачей

Одна задача из плана = одна ветка = один PR. Не делай несколько задач в одной
ветке, даже если они мелкие.

1. **Понять задачу.** Найди её в `docs/refactoring-plan.md`. Прочитай
   актуальный код, который она затрагивает. Если в задаче есть пункт
   «Решение перед началом» или что-то неоднозначно — задай вопросы и дождись
   ответа, прежде чем менять код.
2. **Ветка от свежего `dev`:** `git switch dev`, `git pull`,
   `git switch -c <тип>/<краткое-описание>-<номер issue>`.
   Типы: `fix`, `feat`, `refactor`, `ci`, `docs`, `test`, `chore`.
   Если номера issue нет — спроси.
3. **Сначала тесты.** Для исправления ошибки — тест, который её воспроизводит.
   Запусти тесты и убедись, что новые тесты падают по ожидаемой причине.
   Для чистого рефакторинга — убедись, что существующие тесты покрывают
   затронутое поведение; если нет, сначала добавь тесты на текущее поведение.
4. **Изменения.** Минимальные, только в рамках задачи.
5. **Проверка.** `python -m pytest` и ruff — всё зелёное.
6. **Отчёт и остановка** (см. ниже). Дальше ничего не делать без согласия.

## Согласование перед коммитом — обязательно

Ты **никогда** не делаешь `git commit`, `git push`, не создаёшь и не сливаешь
PR, не меняешь историю (`rebase`, `reset --hard`, `--amend`, force push) без
явного согласия пользователя в этом диалоге. Согласие действует только на
одно названное действие.

Когда изменения готовы, остановись и выдай отчёт:

1. **Что сделано** — по пунктам, своими словами, со ссылкой на критерии
   готовности из плана (какой критерий чем закрыт).
2. **Изменённые файлы** — вывод `git status` и `git diff --stat`, по каждому
   файлу одна строка: что в нём поменялось и зачем.
3. **Как проверить** — команды и ожидаемый результат (сколько тестов, какие
   новые тесты падали до исправления).
4. **Что осталось за рамками** — найденные по ходу проблемы, которые ты
   сознательно не трогал, и известные ограничения.
5. **Вопросы**, если есть.
6. **Предлагаемое сообщение коммита и текст PR** по шаблону
   `.github/pull_request_template.md`.

После этого жди. Пользователь сам просмотрит изменения и напишет, что делать:
поправить, закоммитить, запушить, открыть PR. Если просят поправить — правишь
и снова выдаёшь отчёт (можно короче, только изменения с прошлого раза).

Слияние PR, закрытие issue и любые действия в настройках GitHub делает
пользователь.

## Правила кода

- Не выходи за рамки задачи. Увидел другую проблему — упомяни в отчёте,
  не исправляй.
- Не меняй поведение в задачах типа `refactor`: тесты до и после должны
  проходить без изменений (кроме переноса или переименования).
- Новые настройки: поле в соответствующем `*Config` в
  `system/common/config.py`, чтение в `load()`, строка с комментарием в
  `.env.example` компонента. Файлы `.env` не трогать и не читать.
- Время для таймаутов — `time.monotonic` через подменяемый параметр
  `clock`; в тестах — `FakeClock` из `tests/unit/fakes.py`.
- Безопасность лодки: любое место, где навигация «ничего не делает», должно
  явно отправлять `stop`. Нельзя ослаблять watchdog драйвера, таймаут
  позиции и `_safe_tick`.
- Тесты не должны зависеть от GPIO, сети, MQTT-брокера и камеры.
  Реальное ожидание (`time.sleep`) в тестах — только если без него никак, и
  не дольше долей секунды.
- Зависимости не добавлять без согласия пользователя.
