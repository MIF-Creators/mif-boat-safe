# CLAUDE.md

Инструкции для Claude Code в репозитории `mif-boat-safe`. Читай этот файл
целиком перед любой работой.

## Проект

Учебная система управления флотом автономных лодок в бассейне. Три программы
общаются через MQTT-брокер (Mosquitto):

- `system/navigation_server/` — камера над бассейном, распознаёт ArUco-маркеры
  и публикует позиции лодок (`nav/{id}/position`);
- `system/vehicle/` — код лодки на Raspberry Pi: получает миссию и позицию,
  управляет моторами через GPIO (на ПК без `RPi.GPIO` работает заглушка);
- `system/control_center/` — Flask-сервер и веб-интерфейс оператора;
- `system/common/` — общий контракт: топики (`topics.py`), сообщения
  (`messages.py`), настройки (`config.py`). Изменения здесь затрагивают все
  три программы.

`legacy/` — старый код, не трогать.

Задачи — issue на GitHub: в них спецификация (проблема, где в коде,
критерии готовности) и решения, принятые по ходу. План рефакторинга
`docs/refactoring-plan.md` — карта: этапы, порядок задач, зависимости и
ссылки на issue.

## Окружение

- Python 3.13 (как в CI). Основная машина разработчика — Windows, PowerShell.
- Виртуальное окружение: `venv` в корне репозитория.
- Тесты: `python -m pytest` (из корня репозитория).
- GitHub CLI (`gh`) установлен и авторизован — через него читаются issue.
  Если `gh` недоступен, попроси пользователя вставить текст issue.
- Линтер так же, как в CI: `python -m ruff check system tests`. Правила
  заданы в `pyproject.toml` (`[tool.ruff.lint]`), а не в командной строке.

## Процесс работы над задачей

Одна задача из плана = одна ветка = один PR. Не делай несколько задач в одной
ветке, даже если они мелкие.

1. **Понять задачу.** Прочитай issue вместе с комментариями:
   `gh issue view <номер> --comments`. Комментарии важны: в них
   решения, принятые после создания issue. Найди задачу в
   `docs/refactoring-plan.md`, чтобы увидеть её этап и зависимости; если
   задача зависит от невыполненной — скажи об этом и не начинай.
   Ссылки «задача 3.1 плана» в тексте issue переводятся в номера issue по
   таблицам плана. Прочитай актуальный код, который задача затрагивает.
   Если в issue есть раздел «Решение перед началом» или что-то
   неоднозначно — задай вопросы и дождись ответа, прежде чем менять код.
2. **Ветка от свежего `dev`:** `git switch dev`, `git pull`,
   `git switch -c <тип>/<краткое-описание>-<номер issue>`.
   Типы: `fix`, `feat`, `refactor`, `ci`, `docs`, `test`, `chore`.
   Если номера issue нет — спроси. Исключение — PR только с актуализацией
   документации (`docs/...`): для них issue не нужен, ветка без номера.
3. **Сначала тесты.** Для исправления ошибки — тест, который её воспроизводит.
   Запусти тесты и убедись, что новые тесты падают по ожидаемой причине.
   Для чистого рефакторинга — убедись, что существующие тесты покрывают
   затронутое поведение; если нет, сначала добавь тесты на текущее поведение.
4. **Изменения.** Минимальные, только в рамках задачи.
5. **Проверка.** `python -m pytest` и ruff — всё зелёное.
6. **Актуализация плана** (см. ниже) — в той же ветке, что и задача.
7. **Отчёт и остановка** (см. ниже). Дальше ничего не делать без согласия.

## Актуализация плана и issue

Спецификация задачи — в issue, план — только карта. Поэтому:

- **Задача выполнена:** в таблице этапа в плане в колонке «Статус» —
  «готово». Если это последняя задача этапа — пометить этап «готов» в
  заголовке и в таблице обзора. Подробности о том, как сделано, идут в
  PR, а не в план.
- **Решение, принятое в обсуждении** (ответ на «Решение перед началом»,
  уточнение критериев): предложи в отчёте текст комментария к issue,
  чтобы решение осталось рядом с задачей. Если решение меняет другие
  задачи — предложи комментарии и к ним.
- **Найдено по ходу:** проблемы и идеи на будущее не исправляй, а
  предложи в отчёте тексты новых issue (заголовок, тип, метки, milestone,
  описание по шаблону ниже) и место в плане: этап и номер. Когда
  пользователь пришлёт номера — добавь строки в таблицы плана до
  коммита.
- **Issue и milestones ты не создаёшь и не меняешь** — ни через `gh`, ни
  иначе. Только предлагаешь текст; в GitHub его вносит пользователь.

Формат описания issue:

```markdown
## Проблема

## Где

## Готово, когда

- ...

## Решение перед началом   (если есть выбор, который делает пользователь)

## Зависит от   (если есть)

Задача N.M плана рефакторинга (`docs/refactoring-plan.md`), этап N «...».
```

Типы и метки — только существующие в репозитории. Типы (поле Type):
Bug — неправильное поведение; Feature — новая возможность, заметная
оператору или тому, кто разворачивает систему; Task — работа без
изменения поведения (рефакторинг, CI, документация). Метки: `safety`,
`security`, `refactor`, `infra`, `documentation`, `good first issue`,
`help wanted`, `question`. Меток `bug` и `enhancement` нет.

## Согласование перед коммитом — обязательно

Ты **никогда** не делаешь `git commit`, `git push`, не создаёшь и не сливаешь
PR, не меняешь историю (`rebase`, `reset --hard`, `--amend`, force push) без
явного согласия пользователя в этом диалоге. Согласие действует только на
одно названное действие.

Когда изменения готовы, остановись и выдай отчёт:

1. **Что сделано** — по пунктам, своими словами, со ссылкой на критерии
   готовности из issue (какой критерий чем закрыт).
2. **Изменённые файлы** — вывод `git status` и `git diff --stat`, по каждому
   файлу одна строка: что в нём поменялось и зачем (включая изменения
   плана).
3. **Как проверить** — команды и ожидаемый результат (сколько тестов, какие
   новые тесты падали до исправления).
4. **Что осталось за рамками** — найденные по ходу проблемы, которые ты
   сознательно не трогал, и известные ограничения; для каждой —
   предлагаемый текст issue и место в плане.
5. **Комментарии к issue** — если по ходу принимались решения: текст
   комментария для этой issue (и для других, если решение их касается).
6. **Вопросы**, если есть.
7. **Предлагаемое сообщение коммита и текст PR** по шаблону
   `.github/pull_request_template.md`.

После этого жди. Пользователь сам просмотрит изменения и напишет, что делать:
поправить, закоммитить, запушить, открыть PR. Если просят поправить — правишь
и снова выдаёшь отчёт (можно короче, только изменения с прошлого раза).

Слияние PR, закрытие issue и любые действия в настройках GitHub делает
пользователь.

## Правила кода

- Не выходи за рамки задачи. Увидел другую проблему — упомяни в отчёте,
  не исправляй.
- Не меняй поведение в задачах типа `refactor`: тесты до и после должны
  проходить без изменений (кроме переноса или переименования).
- Новые настройки: поле в соответствующем `*Config` в
  `system/common/config.py`, чтение в `load()`, строка с комментарием в
  `.env.example` компонента. Файлы `.env` не трогать и не читать.
- Время для таймаутов — `time.monotonic` через подменяемый параметр
  `clock`; в тестах — `FakeClock` из `tests/unit/fakes.py`.
- Безопасность лодки: любое место, где навигация «ничего не делает», должно
  явно отправлять `stop`. Нельзя ослаблять watchdog драйвера, таймаут
  позиции и `_safe_tick`.
- Тесты не должны зависеть от GPIO, сети, MQTT-брокера и камеры.
  Реальное ожидание (`time.sleep`) в тестах — только если без него никак, и
  не дольше долей секунды.
- Зависимости не добавлять без согласия пользователя.

## Язык

- На английском: названия веток, сообщения коммитов (формат
  `тип: описание`, например `fix: stop motors when mission is not executing`),
  названия PR и issue, код, комментарии и docstring в коде, имена тестов.
- На русском: общение с пользователем, отчёты, тексты PR и issue.
