# План рефакторинга mif-boat-safe

Документ описывает этапы улучшения проекта и задачи внутри них. Каждая задача
написана так, чтобы её можно было отдать исполнителю (человеку или Claude Code):
что не так, где это в коде и как понять, что задача выполнена. Решение не
расписано — его выбирает исполнитель, согласуя спорные моменты.

Источник истины по статусу — GitHub: issue и milestones. Этот документ —
спецификация. Когда задача заведена как issue, впиши её номер в заголовок.

## Как пользоваться

- Порядок этапов важен, порядок задач внутри этапа — по возможности любой,
  если не указана зависимость.
- Одна задача = одна ветка = один PR в `dev`. PR сливается через squash.
- Пункт «Решение перед началом» значит: прежде чем писать код, нужно
  согласовать выбор с руководителем проекта.
- Чтобы дать задачу Claude Code: «Выполни задачу 2.1 из
  docs/refactoring-plan.md, issue #NN». Процесс и правила остановки перед
  коммитом описаны в `CLAUDE.md`.

### Что поменялось по сравнению с первоначальным планом

- **Инфраструктура перенесена перед контрактом** (была этапом 3, стала 2).
  Причины: запуск компонентов через `sys.path.insert(... "/system/" ...)` не
  работает с путями Windows, а основная машина разработки — Windows;
  в коде 21 неиспользуемый импорт, который будет шуметь в каждом PR;
  для валидации сообщений на этапе 3, скорее всего, понадобится новая
  зависимость, и добавлять её проще в уже упорядоченную сборку.
- **Выделен этап «Надёжность и видимость сбоев»**. В него вошли задачи,
  появившиеся при работе над этапом 1: конечный автомат миссии, перевод
  миссии в `failed` и статус лодки `error` при сбое навигации, запуск лодки
  через systemd. Раньше часть этого была размазана по этапу модульности.
- **Задачи безопасности (security) вынесены в отдельный список** для
  DevSecOps: они не блокируют остальные этапы.

## Этап 0. Порядок в репозитории — готов

Ветки `main` и `dev` синхронизированы и защищены rulesets; CI (pytest, ruff,
Bandit, pip-audit); доступы через команды; шаблон PR; метки, типы задач,
milestone «Stage 1».

Договорённости, которые из этого следуют:

- PR с задачами идут в `dev` и сливаются через squash;
- `dev` → `main` сливается только через merge commit;
- изменения идут только в одну сторону, из `dev` в `main`;
- ключевые слова `Closes #N` в PR в `dev` задачу не закрывают
  (ветка по умолчанию — `main`), задачу закрывают вручную после слияния.

## Этап 1. Безопасность лодки — milestone «Stage 1: Vessel safety»

Готово: #12 (stop при паузе и отмене), #13 (watchdog драйвера),
#14 (устаревание позиции), #15 (ошибки в цикле навигации).

### 1.5 `Waypoint wait action blocks the navigation loop` — #16

- **Тип:** Bug, метки `safety`.
- **Проблема.** Действие `wait` на точке маршрута выполняется через
  `time.sleep(duration)` прямо в `NavigationService._tick`. Пока идёт
  ожидание, цикл навигации заблокирован: пауза и отмена миссии не
  обрабатываются, `stop` не повторяется (watchdog драйвера при этом
  срабатывает — моторы стоят, но навигация «глухая»).
- **Где.** `system/vehicle/services/navigation_service.py`, ветка
  `if action == "wait"` в `_tick`.
- **Готово, когда:**
  - ожидание не блокирует цикл: `_tick` возвращается сразу, состояние
    «ждём до момента T» хранится между итерациями;
  - время ожидания измеряется через подменяемые часы (`clock`,
    `time.monotonic` по умолчанию), в тестах — `FakeClock`;
  - во время ожидания на каждой итерации отправляется `stop`;
  - после ожидания миссия переходит к следующей точке;
  - пауза и отмена во время ожидания срабатывают сразу; если ожидание
    прервано отменой, оно не продолжается при новой миссии;
  - тесты: ожидание не завершается раньше времени; завершается после;
    отмена во время ожидания; новая миссия сбрасывает ожидание.
- **Решение перед началом.** Что делать с ожиданием при паузе и
  возобновлении: продолжить отсчёт с места паузы или начать заново.
  Предлагаемый вариант по умолчанию — начать ожидание заново (проще и
  предсказуемо).

После #16 закрыть milestone «Stage 1».

## Этап 2. Инфраструктура проекта

Цель: проект ставится и запускается одинаково на Windows, Linux и
Raspberry Pi; линтер и форматирование не дают копиться мусору.

### 2.1 `Package the project with pyproject.toml and drop sys.path hacks`

- **Тип:** Task, метки `infra`.
- **Проблема.** Три `main.py` делают
  `sys.path.insert(0, __file__.rsplit("/system/", 1)[0])`. На Windows путь
  содержит `\`, разбиение не срабатывает, и импорт `system.*` при запуске
  файлом ломается. Тесты работают только потому, что pytest запускается из
  корня.
- **Где.** Новый `pyproject.toml` в корне; `system/vehicle/main.py`,
  `system/navigation_server/main.py`, `system/control_center/main.py`;
  `README.md`, `system/README.md` (инструкции запуска); CI.
- **Готово, когда:**
  - есть `pyproject.toml`, проект ставится командой `pip install -e .`;
  - строк `sys.path.insert` в коде нет;
  - каждый компонент запускается командой `python -m system.<компонент>.main`
    из корня на Windows и Linux (проверить хотя бы запуск до попытки
    подключения к брокеру);
  - README обновлены: установка и запуск;
  - CI ставит проект тем же способом;
  - все тесты проходят.
- **Решение перед началом.** Нужны ли консольные команды
  (`[project.scripts]`, например `boat-vehicle`) или достаточно
  `python -m`. По умолчанию — только `python -m`, без переименования пакета
  `system`.

### 2.2 `Consolidate dependencies into pyproject extras`

- **Тип:** Task, метки `infra`. **Зависит от** 2.1.
- **Проблема.** Два расходящихся файла зависимостей. Корневой
  `requirements.txt` содержит неиспользуемые `requests` и `packaging` и не
  содержит `paho-mqtt`. `pytest` попадает в рабочие зависимости, OpenCV и
  Flask ставятся на лодку, где не нужны.
- **Где.** `pyproject.toml`, `requirements.txt`, `system/requirements.txt`,
  CI (в том числе шаг pip-audit), README.
- **Готово, когда:**
  - зависимости описаны в `pyproject.toml`: общие (`paho-mqtt`,
    `python-dotenv`) и группы `vehicle`, `nav`, `control`, `dev`
    (`RPi.GPIO` — в `vehicle` с маркером платформы Linux или отдельной
    группой `rpi`);
  - старые `requirements*.txt` удалены или оставлены одной строкой со
    ссылкой на `pyproject.toml` — по согласованию;
  - pip-audit в CI проверяет то же, что реально ставится;
  - README описывает, что ставить на каждую машину.
- **Решение перед началом.** Удалять ли `requirements.txt` совсем
  (обсудить с DevSecOps: от них зависит pip-audit).

### 2.3 `Enable ruff pyflakes rules and fix findings`

- **Тип:** Task, метки `infra`, `refactor`.
- **Проблема.** CI проверяет только критические правила
  (`E9,F63,F7,F82`). Полный набор `F` находит 21 неиспользуемый импорт и
  одну неиспользуемую переменную.
- **Где.** Настройки ruff (в `pyproject.toml` после 2.1 или
  в `ruff.toml`), CI, файлы с замечаниями.
- **Готово, когда:** правила ruff заданы в конфиге, а не в командной строке
  CI; включён набор `F`; `ruff check` чистый; поведение не изменилось
  (тесты проходят без изменений).

### 2.4 `Enable ruff bugbear and pyupgrade rules`

- **Тип:** Task, метки `infra`, `refactor`. **Зависит от** 2.3.
- **Готово, когда:** включены `B` и `UP`, замечания исправлены, тесты
  проходят без изменений. Если какое-то правило даёт ложные срабатывания —
  отключить его точечно с комментарием, почему.

### 2.5 `Apply ruff format to the codebase`

- **Тип:** Task, метки `infra`. **Зависит от** 2.3.
- **Готово, когда:** `ruff format` применён ко всему коду отдельным
  коммитом без других изменений; в CI добавлена проверка
  `ruff format --check`; хэш форматирующего коммита добавлен в
  `.git-blame-ignore-revs` (после слияния — отдельным мелким PR, когда хэш
  известен).
- **Примечание.** Затрагивает почти все файлы. Делать, когда нет других
  открытых PR, и предупредить команду.

### 2.6 `Run CI on push only for main and dev`

- **Тип:** Task, метки `infra`.
- **Проблема.** `on: push` без фильтра: на каждый PR все проверки
  запускаются дважды (push и pull_request).
- **Готово, когда:** `push` ограничен ветками `main` и `dev`; на PR
  проверки идут один раз; обязательная проверка `tests` в rulesets по-прежнему
  отображается как Required (проверить на тестовом PR).

## Этап 3. Контракт сообщений

Цель: все три программы говорят на одном строго описанном языке; ошибки
во входных данных отсекаются на границе, а не роняют логику внутри.

### 3.1 `Replace status and command strings with enums`

- **Тип:** Task, метки `refactor`.
- **Проблема.** Статусы и команды — строки, наборы не согласованы:
  `executing` в `SharedState` и `in_progress` в `MissionStatusMessage`;
  `accepted`, `waypoint_reached` как события; `pending` и `sent` в пункте
  управления; состояние лодки `idle | executing | paused | error` получает
  на деле `mission.status` с `completed`, `cancelled`, `failed`. Команды
  моторам (`forward`, `stop`...) тоже строки, их легко спутать со статусами.
- **Где.** `system/common/messages.py` (или новый `system/common/enums.py`),
  `system/vehicle/shared_state.py`, сервисы лодки,
  `system/control_center/mission.py`, `system/control_center/static/app.js`
  (отображение статусов).
- **Готово, когда:**
  - есть отдельные `Enum` (на основе `str`, чтобы JSON не менялся):
    статус миссии, событие миссии для пункта управления, состояние лодки,
    команда моторам;
  - в коде нет сравнения статусов и команд со строковыми литералами;
  - формат JSON на проводе согласован и описан в таблице в
    `system/README.md`; если значения меняются, веб-интерфейс обновлён;
  - тесты проходят; добавлены тесты сериализации enum в JSON и обратно.
- **Решение перед началом.** Финальный набор значений каждого enum
  (предложение исполнитель готовит первым шагом и согласует).

### 3.2 `Validate messages at the boundary`

- **Тип:** Task, метки `refactor`, `safety`. **Зависит от** 3.1.
- **Проблема.** `BaseMessage.from_json` делает `cls(**data)`: типы не
  проверяются, лишнее поле роняет разбор (несовместимость при добавлении
  поля), точки маршрута — сырые `dict`. Миссия с точкой без `x` или с пустым
  списком точек принимается и ломает навигацию уже внутри цикла. Каждый
  подкласс дублирует одинаковый `from_json`. Классы `Waypoint`,
  `NeighborInfo`, `ObstacleInfo` объявлены, но не используются.
- **Где.** `system/common/messages.py`, места разбора сообщений во всех
  компонентах, тесты.
- **Готово, когда:**
  - точка маршрута — типизированная модель (`x`, `y` — числа; `action` —
    enum; `params` проверяются для `wait`: `duration > 0`);
  - миссия без точек или с некорректной точкой не принимается;
    лодка отвечает статусом отказа (значение из 3.1) с причиной и не
    меняет текущую миссию;
  - неизвестные поля игнорируются (с записью в лог на уровне DEBUG);
  - дубли `from_json` удалены; неиспользуемые классы удалены или
    используются;
  - тесты на корректные и некорректные сообщения каждого типа.
- **Решение перед началом.** Pydantic v2 (новая зависимость, меньше
  кода) или ручная валидация в dataclass. Рекомендация — pydantic.

### 3.3 `Validate mission requests in control center API`

- **Тип:** Task, метки `bug`. **Зависит от** 3.2.
- **Проблема.** `/api/mission/send` принимает любой JSON с непустыми
  `vehicle_id` и `waypoints`.
- **Где.** `system/control_center/main.py`.
- **Готово, когда:** некорректный запрос получает 400 с понятным
  сообщением (используется та же модель, что в 3.2); неизвестный
  `vehicle_id` (не из `VEHICLE_IDS`) отклоняется; тесты через
  `app.test_client()` (если к этому моменту нет `create_app` — тест
  допускается на текущей структуре, рефакторинг в 5.5).

### 3.4 `Ignore mission status updates for stale missions`

- **Тип:** Bug.
- **Проблема.** Пункт управления обновляет статус активной миссии лодки,
  не проверяя `mission_id`: запоздавшее `completed` от прошлой миссии
  перезапишет статус новой.
- **Где.** `system/control_center/mission.py` (`update_status`) и обработчик
  статусов в `system/control_center/main.py`.
- **Готово, когда:** статус с чужим `mission_id` игнорируется (с записью
  в лог), тест на этот случай.

## Этап 4. Надёжность и видимость сбоев

Цель: система либо работает, либо явно сообщает, что не работает.
Полуживых состояний (лодка стоит, а оператор видит «выполняется») нет.

### 4.1 `Extract mission state machine from MissionService`

- **Тип:** Task, метки `refactor`. **Зависит от** 3.1. (Возможно, уже
  заведена как issue — проверить.)
- **Проблема.** Правила жизненного цикла миссии разбросаны:
  `MissionService` решает pause/resume/cancel, `SharedState.set_mission`
  сам ставит `executing`, `SharedState.advance_waypoint` сам ставит
  `completed`, `NavigationService` решает, что сообщить наружу. В
  `MissionService` смешаны транспорт MQTT и правила.
- **Готово, когда:**
  - все переходы собраны в одном классе без зависимостей от MQTT, потоков
    и JSON; недопустимые переходы явно отклоняются;
  - `MissionService` только принимает сообщения, вызывает автомат и
    публикует результат;
  - тесты автомата — прямые вызовы, без фейкового MQTT; таблица переходов
    описана в docstring;
  - поведение снаружи не изменилось (существующие тесты проходят).

### 4.2 `Fail the mission and report error state on navigation failure`

- **Тип:** Feature, метки `safety`. **Зависит от** 4.1.
- **Проблема.** После #15 ошибка в цикле навигации останавливает моторы,
  но миссия остаётся `executing`, а лодка сообщает обычное состояние.
- **Где.** `NavigationService._safe_tick`, автомат миссии, публикация
  статуса лодки в `system/vehicle/main.py`, отображение в пункте управления.
- **Готово, когда:**
  - если ошибка повторяется дольше заданного времени (настройка, по
    умолчанию несколько секунд), миссия переходит в `failed`, пункт
    управления получает событие с причиной;
  - пока ошибка продолжается, состояние лодки в `VehicleStatusMessage` —
    `error`; после восстановления — обычное;
  - оператор видит это в интерфейсе;
  - тесты на переход в `failed` и на состояние `error`.

### 4.3 `Run vehicle software as a systemd service`

- **Тип:** Feature, метки `infra`.
- **Проблема.** Программа лодки запускается вручную; при падении
  процесса её никто не поднимает.
- **Готово, когда:** в репозитории есть unit-файл systemd (например,
  `deploy/vehicle/boat-vehicle.service`) с `Restart=on-failure` и задержкой
  перезапуска; инструкция по установке на Raspberry Pi в README; программа
  корректно завершается по SIGTERM (моторы останавливаются, GPIO
  освобождается) — с тестом или описанной ручной проверкой.
- **Примечание.** После этой задачи можно пересмотреть выбор в `_safe_tick`
  между «остаться в безопасном состоянии» и «упасть и перезапуститься».

### 4.4 `Make configuration loading predictable`

- **Тип:** Task, метки `bug`.
- **Проблема.** `load_dotenv(override=True)`: файл `.env` перекрывает
  переменные окружения, разово переопределить настройку при запуске нельзя.
  Некорректный JSON в `MAP_OBSTACLES` молча превращается в пустой список.
  Значение по умолчанию адреса брокера разное у компонентов.
- **Где.** `system/common/config.py`, `.env.example` всех компонентов.
- **Готово, когда:** переменные окружения имеют приоритет над `.env`;
  некорректные значения настроек приводят к понятной ошибке при старте
  (с именем переменной), а не к тихой замене; значения по умолчанию
  согласованы; тесты загрузки конфига.
- **Решение перед началом.** Подтвердить смену приоритета (`override`) —
  это меняет поведение для тех, у кого переменные заданы и в окружении,
  и в `.env`.

## Этап 5. Модульность

Цель: у каждого модуля одна ответственность, логику можно тестировать без
железа и сети. Задачи этапа хорошо параллелятся между людьми.

### 5.1 `Introduce a shared MQTT client in common`

- **Тип:** Task, метки `refactor`. Делается тремя PR: общий клиент и
  перевод лодки; перевод навигационного сервера; перевод пункта управления.
- **Проблема.** Три почти одинаковых `mqtt_client.py`. У лодки роутинг по
  точному совпадению топика (wildcard-подписки не работают), у пункта
  управления — по подстроке (`"/status" in topic`).
- **Готово, когда:** один клиент в `system/common/`; роутинг через
  `paho.mqtt.client.topic_matches_sub`; переподписка при переподключении;
  ожидание подключения вместо `time.sleep` после `connect`; хендлеры
  получают разобранное сообщение нужного типа; старые клиенты удалены;
  тесты роутинга без брокера.

### 5.2 `Separate motor driver hardware layer`

- **Тип:** Task, метки `refactor`.
- **Проблема.** `DriveService` смешивает watchdog, логику направлений и
  работу с GPIO; заглушка включается молча, если не удалось импортировать
  `RPi.GPIO` (на Raspberry Pi с забытой библиотекой лодка «работает» без
  моторов).
- **Готово, когда:** протокол драйвера моторов и реализации GPIO и mock;
  реализация выбирается настройкой (`MOTOR_DRIVER=gpio|mock`); при
  `gpio` без библиотеки — ошибка при старте; `DriveService` работает
  через протокол; тесты драйвера используют mock-реализацию вместо подмены
  `_execute`.

### 5.3 `Split navigation server main loop`

- **Тип:** Task, метки `refactor`.
- **Проблема.** Главный цикл `system/navigation_server/main.py` читает
  камеру, распознаёт маркеры, считает координаты, рисует предпросмотр и
  публикует в MQTT. `camera.py` читает `os.environ` при импорте в обход
  конфига; `camera_rtsp_url` в конфиге вычисляется, но не используется.
- **Готово, когда:** обработка кадра — отдельная функция
  `кадр → список позиций`, тестируемая на сохранённом изображении;
  предпросмотр — отдельный модуль; камера получает настройки из
  `NavigationServerConfig`; поведение не изменилось.

### 5.4 `Make coordinate system and marker mapping configurable`

- **Тип:** Bug.
- **Проблема.** `CoordinateSystem` всегда отображает поле на 0–100 и
  использует опорные маркеры 1–4 из кода, хотя размер карты и ID маркеров
  настраиваются — при других значениях координаты и карта в интерфейсе
  разъедутся. Имя лодки жёстко строится как `vehicle_{id маркера}`; у лодки
  `ARUCO_MARKER_ID` нигде не используется. Калибровка выполняется один раз.
- **Готово, когда:** размер поля и опорные маркеры берутся из конфига;
  соответствие маркер → лодка задаётся явно на навигационном сервере
  (например, `VEHICLE_MARKERS=vehicle_0:0,vehicle_1:5`);
  `ARUCO_MARKER_ID` у лодки удалён; тесты преобразования координат.
  Перекалибровка — отдельная задача этапа 6.

### 5.5 `Use app factory in control center`

- **Тип:** Task, метки `refactor`.
- **Проблема.** Состояние пункта управления в глобальных переменных,
  обработка HTTP и MQTT перемешана; API невозможно тестировать без
  запуска всего приложения. `VEHICLE_IDS` не используется, в `app.js`
  захардкожен `vehicle_0`.
- **Готово, когда:** `create_app(state, bus)`; тесты API через
  `test_client()` с фейковой шиной; список лодок для интерфейса берётся из
  конфига.

## Этап 6. Симулятор и новые возможности

Определяется подробнее после этапа 5.

- **Симулятор лодки:** принимает команды моторов, двигает виртуальную
  лодку по простой кинематике, публикует позицию в тот же топик, что и
  навигационный сервер. Позволяет разрабатывать без бассейна и камеры.
  Плюс `docker compose` для локального запуска всей системы.
- **Плавное управление:** раздельная скорость моторов через ШИМ и
  пропорциональный регулятор курса вместо поворотов на месте.
- **Обход препятствий** (сейчас `ObstacleAvoidanceService` — заглушка).
- **Перекалибровка** координат при сдвиге камеры.

## Безопасность (security) — для DevSecOps

Не блокируют этапы, берутся по готовности. Метка `security`.

- **Аутентификация MQTT.** `system/mosquitto.conf`: `allow_anonymous true`
  на `0.0.0.0` — любой в сети может отправить лодке миссию. Пароли (или
  сертификаты) в Mosquitto и настройки во всех компонентах.
- **Доступ к пункту управления.** Сейчас Flask слушает `127.0.0.1` по
  умолчанию; если для работы нужен доступ по сети — решить, нужна ли
  аутентификация оператора.
- **Bandit и pip-audit как обязательные проверки** в rulesets, когда
  станет понятно, что они не дают ложных срабатываний.
